# 提示系统实现思路

## 1. 目标与特点

本系统的目标是实现一种“角色靠近物体时，有概率在角色头顶弹出短提示词”的轻量提示机制。  
提示文本显示在玩家角色下的一个文本子物体上，不直接挂在场景物体上，这样可以保证视觉焦点始终跟随玩家。  
不同物体可以配置不同提示词、不同触发概率和不同触发策略；显示层只负责展示文本，不负责决定什么时候弹出。

整体链路建议为：

`玩家进入触发范围 -> 提示源发起请求 -> 概率判定 -> 玩家提示显示器播提示 -> 自动隐藏`

其中：

- `PromptSource` 负责描述“这个物体附近能弹什么提示”
- `PlayerPromptReceiver` 负责接收附近提示请求并决定是否显示
- `PlayerPromptView` 负责把文本显示在玩家子物体上


## 2. 总体架构

建议将系统拆成以下几个模块：

### 2.1 PromptSource

挂在可触发提示的场景物体上，表示“这是一个能对玩家发出提示请求的物体”。

职责：

- 保存该物体对应的提示词配置
- 保存触发概率、优先级、冷却时间等参数
- 在玩家进入触发区域时发起一次提示请求
- 在玩家离开触发区域时通知接收端结束占用关系

建议字段：

- `sourceId`：提示源唯一标识，便于日志排查
- `promptTexts`：该物体可随机使用的提示词列表
- `triggerChance`：触发概率，范围建议 `0~1`
- `priority`：多个物体重叠时的优先级
- `cooldownSeconds`：同一提示源再次触发前的冷却时间
- `triggerMode`：触发方式，建议先支持 `OnEnter`
- `showDuration`：本次提示显示多久

MVP 阶段建议只做：

- 玩家进入触发区时判定一次概率
- 离开后重新进入，才允许再次触发

这样逻辑最简单，也最符合“靠近时偶尔冒一句话”的效果。




### 2.3 PlayerPromptReceiver

挂在玩家身上，作为提示系统的业务入口。

职责：

1. 接收来自不同 `PromptSource` 的显示请求  
2. 进行最终概率判定与当前状态判断  
3. 决定是否接受本次提示  
4. 把最终文本交给显示层  
5. 处理多提示源竞争关系

建议它对外提供类似接口：

- `TryShowPrompt(PromptRequest request)`
- `ClearPromptFromSource(PromptSource source)`

推荐规则：

- 当前已经有提示在显示时，新请求默认不抢占
- 若新提示优先级更高，则允许覆盖旧提示
- 同一来源在冷却内不可重复触发

这样可以避免玩家站在多个物体交界处时提示不断闪烁。


### 2.4 PlayerPromptView

这是纯显示层，建议挂在玩家下的文本子物体上，例如：

- `Player`
  - `Visual`
  - `HintTextAnchor`

`HintTextAnchor` 下建议直接放一个 `TextMeshPro` 或 `TextMeshProUGUI` 对象，用来显示提示词。

职责：

- 设置文本内容
- 控制显示/隐藏
- 处理简单表现，例如淡入、缩放或描边
- 在显示时跟随玩家一起移动

注意：

- 显示组件只负责“显示什么、隐藏什么时候结束”
- 不负责“为什么显示、该不该显示”

这样能保持业务判断与表现层分离。


### 2.5 PromptRuntimeController

如果你不希望在 `PlayerPromptReceiver` 里堆太多状态，也可以单独拆一个运行时控制器。

它可以负责：

- 当前显示中的提示记录
- 当前来源
- 开始时间与结束时间
- 是否允许被打断

MVP 阶段不一定必须拆；当规则开始变多时再拆更合适。


## 3. 场景组织建议

为了贴合你当前的想法，建议按以下方式组织：

### 3.1 玩家侧

玩家对象上需要：

- `PlayerPromptReceiver`
- 一个用于感应的 `Collider2D` 或由物体侧触发器负责触发
- 一个文本子物体，例如 `HintTextAnchor`

`HintTextAnchor` 建议：

- 默认隐藏
- 位置放在角色头顶稍上方
- 文本宽度控制在短句范围内

如果当前场景里还没有文本子物体，则应由你在编辑器里手动补齐：

- 在玩家下创建 `HintTextAnchor`
- 挂 `TextMeshPro` 或 `TextMeshProUGUI`
- 把该引用拖给 `PlayerPromptView`

不建议由脚本运行时自动创建文本对象。


### 3.2 物体侧

每个需要提示的物体上建议放：

- `PromptSource`
- 一个触发范围 `Collider2D`，并勾选 `Is Trigger`

例如：

- 床：提示“这里似乎能睡一会儿”
- 药瓶：提示“也许它能让我安静下来”
- 门：提示“我现在真的要出去吗”

这样不同物体的文案直接跟物体配置绑定，不需要玩家侧写死判断分支。


## 4. 数据设计

建议先使用 Inspector 配置，后续再决定是否抽资源。

### 4.1 PromptSource 的核心字段

- `List<string> promptTexts`
- `float triggerChance`
- `float showDuration`
- `float cooldownSeconds`
- `int priority`
- `bool allowRepeat`
- `bool triggerOncePerEnter`

字段含义：

- `promptTexts`：允许一个物体有多句候选提示，随机取一条
- `triggerChance`：进入范围时命中概率
- `showDuration`：提示展示时长
- `cooldownSeconds`：避免短时间内反复刷词
- `priority`：多个物体同时触发时决定谁先显示
- `allowRepeat`：同一局运行内是否允许重复显示
- `triggerOncePerEnter`：一次进入范围只判定一次


### 4.2 PromptRequest 运行时结构

建议在运行时封装一个请求结构，便于模块解耦。

可包含：

- `PromptSource source`
- `string text`
- `float duration`
- `int priority`
- `float chance`

好处：

- `PromptSource` 负责产出请求
- `PlayerPromptReceiver` 只消费请求
- 后续若要加入世界状态、角色状态或剧情条件，不需要改显示层接口


## 5. 运行流程

建议的最小运行流程如下：

### 5.1 玩家进入物体触发区

1. 玩家进入某个 `PromptSource` 的触发范围  
2. `PromptSource` 检测到进入事件  
3. 如果本次进入已触发过，则直接忽略  
4. 若未触发过，则构建 `PromptRequest`


### 5.2 进行触发判定

1. `PromptSource` 或 `PlayerPromptReceiver` 执行一次随机概率判定  
2. 若随机结果大于 `triggerChance`，则本次不显示  
3. 若命中，则继续进入显示流程

建议把“最终是否显示”的判定放在 `PlayerPromptReceiver`，这样以后若要接入：

- 主角当前状态限制
- 世界状态限制
- 剧情阶段限制

就不需要把逻辑分散到所有物体组件里。


### 5.3 文案选择

1. 从 `promptTexts` 中随机选一条  
2. 生成本次请求  
3. 提交给 `PlayerPromptReceiver`

文案建议都写成短句，长度控制在玩家移动时也容易读完的范围。


### 5.4 显示提示

1. `PlayerPromptReceiver` 检查当前是否已有提示在播  
2. 若没有，则直接交给 `PlayerPromptView` 显示  
3. 若已有，则比较优先级决定是否覆盖  
4. `PlayerPromptView` 更新文本并显示

显示建议：

- 文本出现后保持短暂可读时间
- 到时后自动隐藏
- 隐藏时清空当前来源记录


### 5.5 离开触发区

玩家离开提示物体时：

- 清理“本次进入已触发”标记
- 不强制立刻把文本关掉

这样体验会更自然，因为玩家刚走出边界时文字还能完整读完。


## 6. 概率与防刷策略

“有概率弹出提示”最容易出现的问题，是提示过密或完全刷不出来，因此建议从一开始就把概率和防刷拆开配置。

### 6.1 概率建议

- 常规环境物体：`0.2 ~ 0.4`
- 关键引导物体：`0.6 ~ 1.0`
- 纯氛围型物体：`0.1 ~ 0.2`

这只是初始建议，最终数值应暴露给 Inspector 调整。


### 6.2 防刷建议

至少加入以下三个限制：

1. 同一来源有冷却时间  
2. 一次进入范围只触发一次  
3. 当前已有提示时，不允许低优先级提示覆盖

这样基本就能解决“角色站在提示区附近时疯狂刷字”的问题。


## 7. 与现有项目规范的兼容方式

该系统建议采用“事件请求 + 显示层订阅”的结构，而不是让场景物体直接去改玩家文本。

推荐依赖方向：

- `PromptSource` 只发请求
- `PlayerPromptReceiver` 只处理业务判断
- `PlayerPromptView` 只负责表现

这样可以满足以下目标：

- 低耦合
- 可测试
- Inspector 可配置
- 后续容易扩展到不同世界、不同角色状态

如果未来需要接入 A3 世界状态，也可以在 `PlayerPromptReceiver` 中增加判断，例如：

- 现实世界显示正常提示
- 意识世界显示扭曲提示
- 高解离状态下降低理性提示出现概率

这类扩展不会破坏当前基础结构。


## 8. 推荐的最小实现顺序

为了优先做出可运行版本，建议按以下顺序实现：

### 阶段 1：先跑通最小链路

- 在玩家下创建文本子物体 `HintTextAnchor`
- 完成 `PlayerPromptView`
- 完成 `PromptSource`
- 完成进入范围触发一次概率判定
- 能在玩家头顶显示一句固定文本并自动隐藏


### 阶段 2：支持每个物体不同提示

- `PromptSource` 支持不同配置
- 支持多个物体各自配置文案
- 支持从候选列表随机选一句


### 阶段 3：补齐防刷与优先级

- 加入冷却
- 加入优先级
- 加入一次进入只判定一次


### 阶段 4：补表现

- 文本淡入淡出


## 9. 验收建议

完成 MVP 后，至少验证以下场景：

1. 玩家靠近床、门、药瓶时，分别能显示不同提示词  
2. 同一个物体不是每次都必定弹词，而是符合配置概率  
3. 玩家短时间反复进出时，不会连续疯狂刷提示  
4. 多个提示区重叠时，最终只显示一个结果  
5. 提示词跟随玩家移动，并在时长结束后正常隐藏


## 10. 总结

这个提示系统适合采用“物体定义内容，玩家统一显示”的方案。  
物体侧负责配置“可能说什么、概率多少、优先级多高”，玩家侧负责决定“当前要不要显示、显示哪一句、显示多久”。  
你现在提出的“把文本子物体放在角色下”是正确方向，因为它能保证跟随感和统一管理。  
MVP 阶段建议先做“进入范围时概率触发一次”的版本，先把体验跑通，再决定是否扩展成更复杂的周期触发或条件触发系统。
